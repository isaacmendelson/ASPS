# ASPS Security Audit — Consolidated CISO Report

**Date:** 2026-05-03
**Repository:** `c:\Jobs\ASPS\GitHub\Software` (branch `main`)
**Scope:** Backend (.NET 8 + NetMQ + EF/MySQL), WebApi (Razor Pages + REST + Keycloak SSO), Browser extension (Chrome MV3), Python desktop agent (Windows), Mobile agents (Android/iOS — spec only), Configuration & secrets, Git history, Dependencies, Deployment.
**Methodology:** Three parallel security audits by senior application security engineers, each focused on a different layer. Findings synthesized below with severity normalization and roll-up.

---

## Executive Summary

ASPS is in a **pre-production state with multiple Critical-severity exposures of production secrets and authentication weaknesses that, in combination, allow remote unauthenticated takeover of the admin tier and the device-fleet messaging plane.** Five Critical findings were identified that warrant immediate action, ahead of any continued feature development.

The product's core security primitives (CurveZMQ for device→backend, Keycloak for admin auth, EF Core parameterized queries, MV3 extension manifest) are correct in concept. The exposures stem from:

1. **Operational regressions** — secrets that were removed in February 2026 were re-introduced in March 2026 in `docker-compose.yml`. There is no automated guardrail against this.
2. **Defense-in-depth gaps** — `TypeNameHandling.Auto` is used pervasively without a `SerializationBinder`; ports 5555/5556 are bound to all interfaces; client↔agent IPC has no localhost authentication.
3. **Hard-coded developer shortcuts** that survived into production code paths — admin allow-list by username, dev-mode login that grants Admin to any name, `RequireHttpsMetadata=false` hardcoded in Program.cs.
4. **Privacy posture for an antiscam product** — `<all_urls>` extension permission, raw browser history collection, GeoIP via plaintext HTTP to a third party — these are not bugs, but they require a privacy story before production launch.

**The "BFG Git History Cleanup" task in JIRA (SCRUM-452) is incomplete** — the leaked secrets remain reachable in git history of the current `HEAD` branch, even after rotation.

## 1. Critical Findings (Detailed)

### 1.1 Newtonsoft.Json `TypeNameHandling.Auto` — RCE chain via CQRS plane
- **CWE-502** (Deserialization of Untrusted Data)
- **Evidence:**
  - `ASPSBackend14_J/Business/Messaging/CQRSGateway.cs` — **60+ call sites** (lines 235, 247, 259, 273, 287, 301, 316, 330, 344, 358, 394, 408, 422, …) all instantiate `new JsonSerializerSettings { TypeNameHandling = TypeNameHandling.Auto }` without a `SerializationBinder`.
  - `ASPSBackend14_J/WebApi/Services/CQRSClient.cs:81-84,168-171` — incoming response deserialized with `Auto`.
- **Risk:** Anyone reaching `tcp://*:5556` (which is bound to **all interfaces**, see 1.5) can submit a JSON payload with `$type` referencing a known dangerous type (`System.Diagnostics.Process`, `ObjectDataProvider`, `WindowsIdentity`) → arbitrary code execution within the Backend or WebApi process.
- **Mitigating factor:** Outbound serialization correctly uses `TypeNameHandling.None`. So `$type` shouldn't normally appear — but the receive side honors it if injected.
- **Fix:** (a) Replace `Auto` with `None` on all CQRS gateway paths; the result types are statically known. (b) For genuinely polymorphic cases (`List<DeviceAlertEntity>`), implement a strict `ISerializationBinder` that allow-lists the expected concrete subclasses.

### 1.2 Hard-coded admin allow-list (`isaac`, `admin`, `asps-admin`) bypasses Keycloak group membership
- **CWE-798, CWE-285**
- **Evidence:**
  - `ASPSBackend14_J/WebApi/Services/AdminClaimsTransformer.cs:8` — `private static readonly string[] AdminUsernames = { "asps-admin", "isaac", "admin" };`
  - `ASPSBackend14_J/WebApi/Program.cs:132-134` — same allow-list duplicated. Comment admits "temporary".
- **Risk:** If realm self-registration is enabled (or any admin can create a user with one of these names), the user automatically gets Admin in ASPS without being in the `Administrators` group. Username `"isaac"` is particularly dangerous because it's a personal name that could clash.
- **Fix:** Remove both lists. Authorize on the `groups` claim with **exact match** against `/Administrators`. The current substring check at `Program.cs:145` (`claim.Value.Contains("Administrators")`) also matches `"NotAnAdministratorsClub"`.

### 1.3 Dev-mode login grants Admin to any username with no password check
- **CWE-287, CWE-489** (Active Debug Code)
- **Evidence:** `ASPSBackend14_J/WebApi/Pages/Login.cshtml.cs:50-92` — when `Keycloak:ClientId` is empty, `OnPostAsync` accepts any non-empty username (Password is bound but never read at line 63-67) and signs in with `new Claim(ClaimTypes.Role, "Admin")` (line 74).
- **Risk:** A misconfigured production deployment (missing env var, secret rotation that nulls the value, container env typo) silently switches the entire app to "any user → admin". The Razor Page is `AllowAnonymousToPage("/Login")` so anyone can hit it.
- **Fix:** Wrap in `#if DEBUG` or behind explicit `ASPS:AllowDevLogin=true` flag. Throw at startup if `IsProduction()` and Keycloak unconfigured.

### 1.4 Keycloak OIDC ClientSecret committed in `appsettings.Docker.json`
- **CWE-798**
- **Evidence:**
  - `ASPSBackend14_J/WebApi/appsettings.Docker.json:12` — `"ClientSecret": "kqWK0iYEB26Ab2Jp0XRvVPtnGvhODjZq"`. File is **not** gitignored (committed in `450b7a9`, Mar 2 2026).
- **Risk:** Anyone with read access to the GitHub repo can impersonate `asps-webapi` against Keycloak, mint admin tokens, pivot into the production admin UI. Repo visibility (public/private) determines blast radius.
- **Fix:** Rotate immediately. Move `ClientSecret` to env var (`Keycloak__ClientSecret`) injected by `docker-compose` from a `.env` file. Treat as active incident — assume compromise.

### 1.5 MySQL root password (`zappa22`) committed in `docker-compose.yml`
- **CWE-798**
- **Evidence:**
  - `docker-compose.yml:13,22,48` — `MYSQL_ROOT_PASSWORD: zappa22` and connection string `password=zappa22`.
  - `ASPSBackend14_J/docs/JIRA-UPDATE-INSTRUCTIONS.md:139,145,151` — same password reused for JIRA admin (`isaac:zappa22@http://187.124.10.197:8080/`).
  - `ASPSBackend14_J/DEVICEALERTKEY-IMPLEMENTATION.md:157` — same.
- **Regression:** Commit `24863e8` (Feb 28) had migrated to `${MYSQL_ROOT_PASSWORD}` env var. Commit `c9859a5` (Mar 8) silently reverted to hardcoded `zappa22` without mentioning it in the commit message.
- **Risk:** Compounded by `SslMode=None` (Finding 4.3 below) — credentials and query results travel plaintext, easily MITM'd.
- **Fix:** Revert to env-var pattern; rotate password (still pending in JIRA SCRUM-453); drop `root` for app — create `asps_app@%` with only DML privileges.

## 2. Authentication & Authorization (High)

### 2.1 All API controllers except `SystemController` are unauthenticated
- **CWE-306** (Missing Authentication for Critical Function)
- **Evidence:** `ASPSBackend14_J/WebApi/Controllers/` — only `SystemController.cs:8` carries `[Authorize(Roles="Admin")]`. Others (`AlertsController`, `UsersController`, `UserDevicesController`, `SimulationsApiController`, `VersionController`) have only `[ApiController][Route(...)]`.
- **Anonymous attack surface:**
  - `GET /api/Users` → enumerate every user
  - `POST /api/UserDevices` → create devices owned by any user key
  - `PUT /api/UserDevices/{keyType}/{keyValue}` → modify monitoring status
  - `POST /api/Alerts/trackurl` → inject arbitrary alerts attributed to any DeviceUid
  - `GET /api/simulations/users?search=` → enumerate users
- **Fix:** Add `[Authorize(Roles="Admin")]` everywhere; for device-originated endpoints use a separate policy validating the device token.

### 2.2 OIDC `RequireHttpsMetadata = false` hard-coded
- **CWE-295, CWE-319**
- **Evidence:** `ASPSBackend14_J/WebApi/Program.cs:93`. The `appsettings.Development.json:8` claims `RequireHttpsMetadata: true` but the code never reads it.
- **Risk:** OIDC discovery + JWKS over HTTP allows MITM-injected signing keys → forged ID tokens.
- **Fix:** `options.RequireHttpsMetadata = !env.IsDevelopment();`

### 2.3 ZMQ ports 5555/5556 bind to all interfaces, no CURVE
- **CWE-306, CWE-319, CWE-668**
- **Evidence:** `Business/Messaging/CQRSGateway.cs:35,50` (`tcp://*:5556`), `NetMQMessageProcessor.cs:34` (`tcp://*:5555`). Comments call them "internal localhost channel" — the binding contradicts the comment.
- **Risk:** Any host on the network connects, issues `CreateUserAdminCommand`, `DeleteUserCommand`, etc. with attacker-chosen `UpdatedBy`. Combined with 1.1 → RCE.
- **Fix:** Bind to `tcp://127.0.0.1:`. Or enable CURVE on these channels — `_curveKeyManager` is already plumbed but never applied (`CQRSGateway.cs:36,41`).

### 2.4 `/DebugClaims` is `[AllowAnonymous]` and dumps every claim
- **CWE-200**
- **Evidence:** `WebApi/Pages/DebugClaims.cshtml.cs:6` + `Program.cs:42`.
- **Fix:** Delete the page or gate behind `[Authorize(Roles="Admin")]`. Add site-wide `X-Frame-Options: DENY`.

### 2.5 `DeviceLogin` logs full token in plaintext
- **CWE-532**
- **Evidence:** `WebApi/Pages/DeviceLogin.cshtml.cs:163,182` — `_logger.LogInformation("Response received: {Response}", responseJson)` where the response contains `token`. Default log level `Information`.
- **Fix:** Log only `Status` and message length; never the body.

### 2.6 `DeviceLogin` allows binding any DeviceUid to a known email
- **CWE-287**
- **Evidence:** `WebApi/Pages/DeviceLogin.cshtml.cs:80-130` — anonymous; backend doesn't email-confirm new device-binding for an existing user.
- **Fix:** Require email-confirmation token before binding a new DeviceUid to an existing user. Tighten rate-limit (currently 3/min — too generous for new-account binding).

### 2.7 24h token + 7-day silent refresh, no revocation primitive
- **CWE-613**
- **Evidence:** `appsettings.json:34-37` (1440 + 10080 minutes); `TokenStore.cs:136-181`. No admin revocation endpoint found.
- **Fix:** Add admin revocation endpoint; bind token to device's CURVE public key so a stolen token alone is useless.

### 2.8 SignalR Hub has no `[Authorize]` and accepts query-string token
- **CWE-200, CWE-287**
- **Evidence:** `WebApi/Hubs/NotificationsHub.cs:29-30,69-73`.
- **Fix:** `[Authorize(Roles="Admin")]` on the hub. Move device tokens to `Authorization: Bearer` or SignalR `accessTokenFactory`.

## 3. Cryptography & Key Management (High/Medium)

### 3.1 Server CURVE private key unencrypted on disk; no rotation procedure; no ACL on Windows
- **CWE-312, CWE-321**
- **Evidence:** `Business/Services/CurveKeyManager.cs:131-150`. On Linux `chmod 0600` applied at `:147-149`; **on Windows no ACL is set** — file inherits parent dir, often readable by `BUILTIN\Users`.
- **Fix:** (a) Apply `FileSystemAccessRule` on Windows. (b) Wrap secret with DPAPI (`ProtectedData.Protect`). (c) Document and implement a rotation procedure.

### 3.2 Device public keys are not pinned — only the server is authenticated
- **Evidence:** `RealTimeAlertListener.cs:96` calls `_curveKeyManager?.ApplyServerCurve(_routerSocket)` (server-side only). No `ZAP` handler, no client public-key allowlist. NetMQ default = "any client knowing our server public key may connect".
- **Risk:** CURVE encrypts but does not authenticate the device. Stolen `BACKEND_SERVER_PUBLIC_KEY_Z85` (treated as public) + exfiltrated device token = full impersonation.
- **Fix:** Per-device CURVE keypair issued at registration, stored in `UserDevices.DevicePublicKey`, validated via NetMQ's ZAP.

### 3.3 CURVE TOFU + plaintext fallback on first run (Python desktop agent)
- **CWE-295, CWE-300**
- **Evidence:** `apps/desktop/win/src/auth_manager.py:75-84`; `config.py:73`. Comment: *"No key — first connection is unencrypted; key received from backend RequestToken response."*
- **Risk:** Trust-on-first-use over plaintext. A network attacker on first run swaps the server public key, then MITMs forever. Operator can downgrade to plaintext by clearing the key file.
- **Fix:** Pin a known-good server CURVE public key at install time as a compiled constant. Refuse to run if pinned key absent. Add signature-verified key-rotation protocol.

### 3.4 MySQL connection: `SslMode=None` and `AllowPublicKeyRetrieval=True`
- **CWE-319, CWE-295**
- **Evidence:** `docker-compose.yml:48`; `appsettings.Development.json:3`.
- **Fix:** `SslMode=Required` (or `VerifyFull`); `AllowPublicKeyRetrieval=False`; provision MySQL with CA-signed cert.

### 3.5 Cookie `SecurePolicy = SameAsRequest`
- **CWE-614**
- **Evidence:** `WebApi/Program.cs:81`.
- **Fix:** `CookieSecurePolicy.Always` for any non-Development environment.

### 3.6 HSTS not configured; only enabled in production with default 30-day max-age
- **Evidence:** `Program.cs:249-252`.
- **Fix:** `services.AddHsts(o => { o.MaxAge = TimeSpan.FromDays(365); o.IncludeSubDomains = true; o.Preload = true; });`

## 4. Input Validation & DoS (High)

### 4.1 No payload size limit, no `MaxDepth`, no `MaxRequestBodySize` anywhere
- **CWE-770, CWE-400**
- **Evidence:** Repo-wide search for `MaxRequestBodySize|Options.MaxMsgSize|MaxDepth` returned **zero matches**.
- **Risk:** A malicious peer streams 1 GB JSON to port 50001 (or `POST /api/Alerts/trackurl`) → OOM. With `TypeNameHandling.Auto` plus deeply-nested generics → exponential type instantiation.
- **Fix:** Set `socket.Options.MaxMsgSize = 1MB` on every NetMQ socket. Set `MaxDepth = 32` and a `MaxStringLength` on every JsonSerializerSettings. Configure `KestrelServerOptions.Limits.MaxRequestBodySize`.

### 4.2 Rate-limiter keyed on attacker-controlled DeviceUid; no rate-limit on alerts
- **CWE-770**
- **Evidence:** `Business/Services/RateLimiter.cs` — keys are `$"{messageType}:{deviceUid}"` from payload. Only `RequestToken`/`RegisterDevice`/`RefreshToken` are rate-limited; alerts have no limit.
- **Fix:** Combine IP + CURVE-client-public-key + DeviceUid for the key. Add rate limit for alert ingestion (e.g., 60/min/device).

### 4.3 Plaintext device tokens persisted in DeviceAlerts table
- **CWE-312**
- **Evidence:** `Business/RealtimeAnalysis/AlertPersistenceActor.cs:78,102,135` — `Token = vm.Token` saved with every alert.
- **Fix:** Don't persist; if audit needed, store SHA-256(token).

## 5. Web App / XSS (Medium-High)

### 5.1 Roadmap Viewer export uses `JavaScriptEncoder.UnsafeRelaxedJsonEscaping` — stored XSS in exported HTML
- **CWE-79, CWE-693**
- **Evidence:** `WebApi/Pages/Roadmaps/Edit.cshtml.cs:177-188,237-247`. Inner script tag escape (`safeJs`) at `:191` does NOT apply to the `initialPayload` JSON.
- **Risk:** An admin creates a roadmap with `Name` or `Description` containing `</script><script>alert(1)</script>`, then exports the HTML viewer. Anyone opening the file (intended for offline distribution) executes the JS.
- **Fix:** Replace `UnsafeRelaxedJsonEscaping` with `JavaScriptEncoder.Default` (escapes `<` to `<`).

### 5.2 No global CSP / X-Frame-Options / Permissions-Policy
- **Fix:** Add CSP middleware: `default-src 'self'; script-src 'self'; frame-ancestors 'none'`.

### 5.3 Browser extension content script: `innerHTML` of `score`/`riskType` from agent — XSS sink
- **CWE-79**
- **Evidence:** `apps/extension/chrome/content.js:179-194,205,248`. Server-controlled `score` is interpolated into a template-string `innerHTML`.
- **Risk:** Backend (or MITM on the local WebSocket — see 6.1) sends `score: "<img src=x onerror=alert(1)>"` → XSS in the privileged content script context.
- **Fix:** Build the warning UI with `document.createElement` + `textContent`; or coerce inputs (`String(score)` after `typeof === 'number'`).

## 6. Client agents — Privacy & Local Authentication (High)

### 6.1 `ws://localhost:{8080..8484}` between extension and Python agent — no auth, no Origin check
- **CWE-345, CWE-940**
- **Evidence:** `apps/extension/chrome/services/ConnectionService.js:14,87`; `apps/desktop/win/src/extension_server.py:109-115`.
- **Risk:** Any local process can connect, send `{"type":"user_auth","email":"victim@..."}` — agent trusts the email and binds the device to victim's account. Account takeover on multi-user box.
- **Fix:** Per-install secret token written to `%APPDATA%\AntiScam\extension-secret.txt` (ACL'd to current user); validated on every WebSocket OPEN. Reject non-`chrome-extension://` Origin.

### 6.2 Email "authentication" via extension → agent
- **CWE-287**
- **Evidence:** `apps/desktop/win/src/handlers/extension_handler.py:96-105` — agent trusts `email` from extension without verification.
- **Fix:** OAuth flow (Google/Microsoft) proving email ownership; send signed ID token to backend. Never trust self-claimed email.

### 6.3 Browser extension `<all_urls>` permission + `tabs` permission
- **CWE-272, CWE-359**
- **Evidence:** `apps/extension/chrome/manifest.json:14-16,8`; `background.js:126-141`.
- **Risk:** Total surveillance posture if extension is ever compromised (Web Store account takeover). Reading every tab's URL/title and forwarding to agent is privacy-overbroad.
- **Fix:** `optional_host_permissions` with per-domain consent. Strip query strings before transmit. Default `REMOTE_ACCESS_BROWSER_TABS_MODE` to `active_session_only`.

### 6.4 Browser-history scraping: 100 entries per browser, sent on demand
- **CWE-359**
- **Evidence:** `apps/desktop/win/src/browser_history.py:122-127,280-307`.
- **Fix:** Filter localhost/private IPs/sensitive domains. User-visible toggle. Hash URLs client-side; only send hashes unless domain matches a server watchlist.

### 6.5 GeoIP via plaintext HTTP to third-party `ip-api.com`
- **CWE-319, CWE-359**
- **Evidence:** `apps/desktop/win/src/remote_monitor.py:138-153`.
- **Fix:** Use the existing offline `geoip2` MaxMind DB (already in `requirements.txt:26`), or HTTPS.

### 6.6 Possible hardcoded Google `client_secret` in shipped binary
- **CWE-798** (potential)
- **Evidence:** `apps/desktop/win/src/google_auth.py:18,270-271,340-341`.
- **Fix:** Re-register OAuth client as "Desktop app" type in Google Cloud Console. Use PKCE flow. Remove `GOOGLE_CLIENT_SECRET` entirely.

## 7. Supply Chain (Critical/High)

### 7.1 No code-signing of installer or EXE
- **CWE-494, CWE-347** (potential — depends on shipped pipeline)
- **Evidence:** `apps/desktop/win/build_release.py:147-170`; `installer.iss` has no `SignTool` directive.
- **Risk:** SmartScreen "unrecognized publisher" trains users to ignore warnings. Compromise of GitHub Releases swaps binary undetected. SHA-256 checksums in same channel = same risk.
- **Fix:** Buy EV code-signing cert. Sign both `AntiScam.exe` and `AntiScamDesktop-Setup-x.x.x.exe` in CI.

### 7.2 No auto-update mechanism
- **CWE-1357**
- **Evidence:** `apps/desktop/win/INSTALL.md:128-138` — manual updates ("Replace `AntiScam.exe`").
- **Risk:** Vulnerabilities cannot be patched at scale. Users on stale versions retain known auth/CURVE flaws.
- **Fix:** Signed update channel. EXE checks `https://updates.antiscam.io/win/version.json`; verify Authenticode + an embedded public-key signature on the manifest.

### 7.3 Cleanup commit reverted within 8 days; no CI guardrail
- **CWE-1357** (process)
- **Evidence:** Feb 27-28: commits `99915d2`, `24863e8`, `5516619` removed secrets. Mar 8: commit `c9859a5` silently re-hardcoded `zappa22` in `docker-compose.yml`.
- **Fix:** `gitleaks` or `trufflehog` as pre-commit hook + required GitHub Actions check.

### 7.4 Browser extension distribution channel undocumented
- **Evidence:** `apps/desktop/win/INSTALL.md:88-90` references the Chrome Web Store but no extension ID, no signing key escrow procedure.
- **Risk:** Web Store account takeover (no documented MFA) ships malicious update to all users. Compounded by 6.3 (`<all_urls>`).
- **Fix:** Hardware MFA on Web Store dev account. Two-person review release process.

## 9. Mobile Spec Threat Model (Design — High)

Reviewed `docs/ARCHITECTURE.md` §16 and `docs/ASPS_DATA_FLOW.md` §10. No code yet — review of spec only.

### 9.1 Android Accessibility Service for URL extraction
- `BIND_ACCESSIBILITY_SERVICE` is the most powerful Android permission outside of system app. Google Play Protect now flags non-disability accessibility usage.
- Spec doesn't define: per-domain consent, audit log, default-off mode, user-visible toggle.
- **Fix:** Spec a least-privilege design: fire only on URL-bar `TYPE_VIEW_TEXT_CHANGED` from a hard-coded list of browser packages; emit ONLY URL-bar text; audit log.

### 9.2 SMS reading (`READ_SMS` + `RECEIVE_SMS`)
- Google Play SMS Permissions Policy restricts to default SMS handler or specific exempt categories. ASPS is neither.
- Spec sends full SMS body to backend — privacy red flag.
- **Fix:** On-device classifier first; only forward body if flagged. Apply for Play Store SMS exemption with clear justification, or pivot to "user pastes SMS to check" UX.

### 9.3 ZMQ-CURVE on JeroMQ / SwiftyZeroMQ — verify lib supports CURVE
- JeroMQ doesn't support CURVE in all versions.
- **Fix:** Verify before Sprint 1.

### 9.4 No spec for pinned server CURVE public key distribution on mobile
- TOFU on mobile networks is worse than corporate desktop.
- **Fix:** Bake server public key into the app binary; signature-verified rotation.

### 9.5 No device revocation flow specified
- **Fix:** Add to spec before Sprint 1.
