## Bug 1: CurveMQ Key Format Mismatch (Phase 1 / Phase 4)
- **What was broken:** CurveMQ encryption between Desktop App (pyzmq) and Backend (NetMQ) silently failed. No error messages, just timeouts.
- **Why it broke:** During initial Phase 1 investigation, CurveMQ was disabled to isolate communication issues. In Phase 4, when re-enabling, the client needed Z85-encoded server public key distributed correctly and ephemeral client keypairs generated per socket.
- **How it was fixed:** apply_curve_client() shared helper, ephemeral keypairs via zmq.curve_keypair(), CURVE options set BEFORE socket.connect(), SERVER_PUBLIC_KEY_Z85 from config/env var.
- **Impact:** Complete communication failure -- all ZMQ messages dropped silently
- **Files:** zmq_client.py, notification_client.py, config.py, appsettings.json
- **Recommendation:** Add CURVE handshake logging to Backend (NetMQ side) so key mismatches produce explicit error messages instead of silent timeouts.

## Bug 2: asyncio.run() Thread-to-Asyncio Bridge Failure (Phase 2)
- **What was broken:** Notifications from Backend (received on ZMQ SUB thread) never reached WebSocket clients in the Extension.
- **Why it broke:** `notification_handler.py` used `asyncio.run()` to call the async `broadcast()` method. `asyncio.run()` creates a NEW event loop -- but WebSocket clients are registered on the MAIN event loop. The broadcast ran on an isolated loop with zero clients.
- **How it was fixed:** Replaced `asyncio.run()` with `asyncio.run_coroutine_threadsafe()`. Main event loop is injected from `main.py` into NotificationHandler at startup.
- **Impact:** 100% of analysis results lost -- the single most critical bug
- **Files:** notification_handler.py, main.py
- **Recommendation:** This is a Python-side Desktop App issue, not a server issue. However, the server team should be aware that the Desktop App's notification pipeline was completely broken. If the server team observes "notifications published but never acknowledged," this was the cause.

## Bug 3: Hardcoded Token UUID (Phase 3)
- **What was broken:** Desktop App sent alerts with a hardcoded test UUID token instead of acquiring a real token from Backend.
- **Why it broke:** During development, a placeholder UUID was used. It was never replaced with the RegisterDevice/RequestToken flow.
- **How it was fixed:** Implemented proper RegisterDevice -> RequestToken two-step flow. Hardcoded UUID completely removed. Empty token fallback with clear warning.
- **Impact:** Backend rejected all alerts due to invalid token (or accepted them under a wrong/nonexistent device)
- **Files:** zmq_client.py, auth_manager.py, config.py
- **Recommendation:** Server should return explicit error messages when token validation fails (e.g., "Invalid token", "Device not registered"). Currently, the response format is ambiguous.

## Bug 4: recv() vs recv_multipart() on ZMQ SUB Socket (Phase 2)
- **What was broken:** ZMQ SUB socket used two sequential `recv()` calls instead of atomic `recv_multipart()`.
- **Why it broke:** ZMQ PUB/SUB sends multipart frames (topic + body). Two sequential recv() calls can desync if a partial message arrives or if the thread is preempted between calls.
- **How it was fixed:** Replaced dual `recv()` with single `recv_multipart()` call.
- **Impact:** Intermittent message corruption on the notification channel
- **Files:** notification_client.py
- **Recommendation:** Ensure Backend's NotificationPublisher sends messages as proper multipart frames (topic frame + body frame). Document the expected frame format.

## Phase 5 Reliability Improvements (Summary)
- ZMQ REQ Lazy Pirate recovery (socket reset after timeout)
- WebSocket PendingResults store (results delivered after Extension reconnects)
- Chrome service worker alarm-based keepalive backup
- MessageQueue persistence via chrome.storage.session

## Recommendations for Server Team
1. Add CURVE handshake diagnostic logging to NetMQ side
2. Return explicit error messages for token validation failures
3. Document the ZMQ PUB/SUB multipart frame format for the notification channel
4. Consider adding a health-check endpoint on the ZMQ REQ port (e.g., respond to a "Ping" message type)
5. Document the expected RegisterDevice/RequestToken response format (field names, status codes)
6. Consider adding a notification acknowledgment mechanism so the server knows results were received
